# TeleBT — نموذج واجهة Telegram للمرحلة الأولى

بوت Python تجريبي يعرض واجهات إدارة الأجهزة والألعاب والأحداث والبروكسي والخطط والاشتراكات باللغتين العربية والإنجليزية. تحفظ الخدمات الوهمية البيانات المؤكدة محلياً في `mock_data/*.json`. **لا توجد عمليات إرسال أحداث أو فحص شبكة أو دفع أو جدولة تنفيذية.** رسائل المعاينة والفحص تحمل وسم التجربة ولا تمثل نتيجة HTTP فعلية.

## المتطلبات

- Python 3.10 أو أحدث.
- Telegram bot token للتجربة اليدوية في محادثة خاصة.
- اعتماديات `requirements.txt`: `python-telegram-bot==22.8` و`tzdata` للمنطقة الزمنية على Windows. مرجع المكتبة: [PyPI](https://pypi.org/project/python-telegram-bot/22.8/).

## التشغيل على Windows PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

ضع رمز البوت الحقيقي في `TELEGRAM_BOT_TOKEN` داخل `.env` المحلي فقط. عدّل `BOT_USERNAME` لتوليد رابط الإحالة، و`SUPPORT_LINK_1` و`SUPPORT_LINK_2` إلى رابطَي دعم تملكهما. قيم `example_*` في المثال تُعامل كغير مضبوطة، وتظهر رسالة إعدادات واضحة بدل روابط مختلقة.

```powershell
$env:PYTHONPATH = "src"
.\.venv\Scripts\python.exe -m telebt.main
```

على macOS/Linux استخدم `.venv/bin/python` و`export PYTHONPATH=src`. أول `/start` يطلب اختيار اللغة. أي `/start` أثناء مسودة غير مؤكدة يلغي المسودة ويوضح ذلك. تظل البيانات المؤكدة في `mock_data/` بين إعادة التشغيل، أما مسودات الحوار فتُحفظ في الذاكرة فقط.

## الاختبارات

```powershell
$env:PYTHONPATH = "src"
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

تغطي الاختبارات التحقق من المعرّفات والقوالب والفواصل، التخزين المفقود أو التالف، الصلاحيات، الحذف التبعي، حفظ المالية عند انتهاء المهلة، حساب المواعيد والتمديد والطابور، تدفقات الواجهة ثنائية اللغة، وبناء محوّل Telegram دون اتصال شبكة. اختبارات Telegram اليدوية تحتاج رمز بوت خاصاً بك ولم تُنفَّذ تلقائياً.

## بنية المشروع

- `src/telebt/telegram_adapter.py`: طبقة Telegram وحدها؛ تستقبل updates وترسل شاشات وأزرار.
- `src/telebt/ui.py` و`locale.py`: الحوارات، التنقل، الترجمة، callback IDs ثابتة.
- `src/telebt/interfaces.py` و`models.py`: عقود الخدمات وDTOs للمرحلة التالية.
- `src/telebt/services.py`: Mock Services وصلاحيات عمليات البيانات والحذف التبعي.
- `src/telebt/storage.py`: JSON محلي مع قفل عملية واحدة وكتابة ذرية.
- `src/telebt/validation.py` و`schedule.py`: التحقق وحساب المواعيد دون scheduler.
- `tests/`: اختبارات وحدات وتدفقات UI ومحوّل Telegram.

ملفات `mock_data/` تنشأ تلقائياً عند التشغيل، ويُنشأ كتالوج ألعاب وهمي `catalog_games.json`. يمكن حذف مجلد البيانات التجريبية يدوياً لإعادة البدء؛ لا تستخدم بيانات عملاء حقيقية فيه. لا تُحمّل هذه الملفات إلى بيئة إنتاج ولا تعتمد عليها للتزامن واسع النطاق أو الاحتفاظ الإنتاجي.

## وضع المطوّر

ضع `DEV_MODE=true` وTelegram user IDs المصرّح لها صراحة في `DEV_TELEGRAM_USER_IDS`، مثل `123456789,987654321`. لا تُستخدم قيم المثال لحسابات حقيقية. أرسل `/dev` من حساب مصرح له. عند `DEV_MODE=false` أو غياب المعرّف تُرفض أوامر المطوّر وcallback IDs الخاصة به.

يمكن من `/dev` محاكاة مستخدم جديد/نشط/منتهٍ، تقدم 32 يوماً، تمديد اشتراك شهري، وضع أسبوعي في طابور FIFO، نفاد الحصة وتجددها، رصيد تجريبي، وفشل عملية مجدولة. من تفاصيل بروكسي محفوظ يستطيع المطوّر ضبط **نتيجة فحص محاكاة** ناجحة أو فاشلة؛ لا يحدث اتصال شبكة. التحول إلى مستخدم جديد أو انتهاء شهر المهلة يمسح البيانات التشغيلية الوهمية فقط، ويحتفظ بالرصيد والسجل المالي والإحالات المالية.

الأسعار والمدة والحدود المبدئية قابلة للتغيير من متغيرات `PLAN_*` في `.env`، ونسبة الإحالة من `REFERRAL_RATE_PERCENT`. رابط الإحالة يسجل مستخدماً محالاً واحداً عند دخوله لأول مرة فقط، دون احتساب مكافأة مالية فعلية. هذه الإعدادات تغير العرض والمحاكاة فقط، ولا تخصم مالاً أو تنفذ شراءً. تكوين نافذة الحصة عند تمديد نفس النوع يحتاج قراراً قبل Backend حقيقي؛ انظر `ASSUMPTIONS.md`.

قواعد شكل المعرّفات قابلة للضبط من `VALIDATION_PATTERN_GAID` و`VALIDATION_PATTERN_IDFA` و`VALIDATION_PATTERN_IDFV` و`VALIDATION_PATTERN_UID` (لـAppsFlyer) و`VALIDATION_PATTERN_SINGULAR`. استخدم `VALIDATION_RULES_VERSION` لتسمية إصدار القواعد عند كل تغيير؛ القيمة الافتراضية `phase1-v1`. يُطبَّق التعبير النمطي على القيمة الكاملة بعد إزالة الفراغات الخارجية، ولا يثبت صحة المعرّف لدى المنصة. تُحفظ صيغ UUID الافتراضية بأحرف صغيرة كما في السابق؛ النمط المخصص يحتفظ بحالة الأحرف المقبولة فيه. يحدد `VALIDATION_MAX_INTERVAL_MINUTES` الحد الأعلى للفاصل؛ افتراضياً `525600` دقيقة (365 يوماً). تُرفض الإعدادات الفارغة أو التعبيرات غير الصالحة أو الحدود غير الموجبة عند بدء التشغيل. راجع `.env.example` للقيم الافتراضية؛ غيّر رقم الإصدار مع أي تغيير في القواعد واحتفظ بنسخة الإعدادات إذا احتجت الرجوع إليها.

## قائمة تجربة Telegram اليدوية

1. افتح `/start` لأول مرة، بدّل العربية/الإنجليزية، وتحقق من عناصر القائمة التسعة ورسائل الخطأ والرجوع والإلغاء.
2. ابحث عن اسم لعبة جزئي على Android وiOS، جرّب نتائج متعددة وحالة عدم وجودها.
3. في حساب مطوّر نشط أضف Android وiOS مع معرفات صالحة وخاطئة، ثم اربط ألعاب AppsFlyer وAdjust وSingular وتحقق من حقولها المختلفة.
4. افتح حدثاً ثابتاً ومتغيراً وشراءً وحدثاً مخصصاً؛ تحقق من وسم عدم الإرسال وعدم تغير الحصة.
5. أضف بروكسياً دون فحص، عدّله، اربطه بجهاز، ثم احذفه وافحص بقاء الجهاز. جرّب فحصاً غير محفوظ ونتائج المحاكاة الخاصة بالمطوّر.
6. أنشئ خطة موحدة وأخرى بفواصل مستقلة، عدّل مسودة قبل الحفظ، راجع UTC والتوقيت المحلي، ثم عدّل عملية غير محاوَلة واحذف خطة بالتأكيد.
7. جرّب الاشتراك الجديد والمنتهي والرصيد والإحالات وطابور الاشتراكات ونفاد الحصة، ثم تقدم الزمن وتحقق من بقاء المالية بعد حذف البيانات التشغيلية.
8. افتح طرق الإيداع الثلاثة ورابطَي الدعم، وأعد تشغيل البوت للتحقق من عودة البيانات المؤكدة.

## حدود المرحلة الأولى

لا Backend أو REST API، لا PostgreSQL، لا تكاملات AppsFlyer/Adjust/Singular، لا HTTP event requests، لا proxy network check، لا دفع، لا Jobs أو APScheduler، لا لوحة إدارة، ولا نشر VPS. لا يُنتج الزر التجريبي `HTTP 200` وهمياً ولا يستهلك حصة. أي تشغيل إنتاجي يحتاج الخطوات في `PRE_RELEASE_CHECKLIST.md` وخدمات مصرح بها منفصلة عن هذا النموذج.
